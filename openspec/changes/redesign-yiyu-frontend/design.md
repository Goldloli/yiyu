# Design

## Context

参见 `proposal.md`。当前前端由 React 多窗口 hash 路由、Zustand、共享 IPC 契约和 Rust 设置服务构成；`Settings` 已有 `theme`、`motion`、`windowGlass` 及 revision，尚无自定义背景字段或本地选图契约。主窗口默认 `980 × 660`、最小 `760 × 500`，浮窗具有独立尺寸与非激活行为。

用户确认的视觉方向和效果稿位于 `docs/design/yiyu-frontend-redesign.md`。参考图表达材质和布局意图，不是可直接实现的源码或独立背景素材。详细可观察行为以本变更的两个 capability specs 为准。

## Goals / Non-Goals

**Goals:**

- 在四类窗口共用可调校的浅深主题、玻璃材质和状态组件，并保留现有翻译及系统交互。
- 将本地背景图片作为受限制、可恢复的外观能力接入已有设置 revision 和多窗口事件。
- 通过浏览器 mock、实际窗口和平台验证共同决定可行的模糊效果与性能预算。

**Non-Goals:**

- 不重写翻译协议、Provider、历史业务或更新器，不增加 OCR、朗读或其他 AI 任务。
- 不内置远程壁纸服务、背景视频或将用户图片上传到任何服务。
- 不把概念图当成可直接交付的应用，也不以纯浏览器 mock 替代平台窗口验收。

## Decisions

### D1. 视觉系统与窗口布局

维护一套语义化 tokens：主题底色、玻璃表面、分隔线、主次文字、强调、焦点、错误和遮罩。浅色与深色各自定义值，强调色用于主要操作与状态。玻璃以半透明底色和背景模糊为主，仅保留轻边界与低强度阴影；模糊 18–26px 是参考材料中的初始调校范围，不作为跨平台强制数值。

主窗口采用左侧历史和原文/译文工作区；空间不足时将历史折叠为明确入口，并允许工具栏重新排布。浮窗、设置与 onboarding 使用同一组件语言，分别按各自窗口职责调整密度。确认、输入对话框、下拉菜单和通知也使用相同的主题与轻玻璃表面；系统授权对话框保留原生样式。普通控件与主要文字优先保持可读尺寸，非必要动画遵循现有 `motion` 设置。

快捷浮窗以原文、译文和必要操作为主，删除重复的状态与说明；取词、权限或模型配置失败时在浮窗中持续显示原因和可执行入口。菜单栏使用原生分组菜单，展示实际配置的快捷键，并直达翻译、主窗口和设置。

**原因**：一次性重建语义与组件可以避免四个窗口各自复制效果，也使后续浅深主题调整保持一致。继续在现有页面中零散追加颜色和阴影容易再次产生不一致。

### D2. 背景范围和主题关系

新安装默认使用内置自然风景，用户可选择其他内置风景、无背景或本地图片。主窗口、设置、首次配置和快捷浮窗在玻璃层后方使用同一背景；浅色和深色采用各自的内容表面与遮罩。浮窗使用更克制的背景显示和足够对比度，并在用户关闭玻璃或背景不可用时回退至主题底色。

背景属于单一全局外观配置，不与浅深主题各自保存独立图片。实际渲染需验证浅色字/深色字在亮图、暗图及高对比图上的可读性；必要时提高面板遮罩，而不是修改用户源图。

**备选方案**：每主题独立图片和每窗口独立开关增加配置复杂度，目前没有用户需求。浮窗背景需要同时验证非激活窗口、滚动和定位行为。

### D3. 图片生命周期与事务

由受限 Tauri 命令和系统选图路径读取用户明确选中的本地 JPEG/PNG，校验真实格式、文件大小和解码尺寸；上限及错误文案由实现时的性能测试确定并在界面说明。应用将通过校验的图片复制到应用数据目录下受控的背景资源区，配置只保存应用管理的资源标识和必要元数据，不保存图片二进制或原始用户路径。

选择/预览先在内存中准备候选图片；应用时在设置服务的提交边界内校验 `expectedRevision`，写入受控候选文件并原子持久化新资源标识。失败或版本冲突仅清理本次候选，保留旧背景；提交成功后清理不再使用的旧应用副本并通知窗口。移除走明确的清除命令，避免依赖可选字段的 `null`/缺失歧义。始终不移动、修改或删除用户选中的源文件。

窗口只接收经受限资源通道生成的可用资源引用；不授予前端任意文件系统读取权限，不允许路径穿越或任意删除。明确评估现有 CSP、资源协议范围和最小 capabilities；不要假设仅添加 `asset:` 到 CSP 就足以安全地暴露图片。无效文件、磁盘错误、旧版本请求、已失效资源都回退并显示可恢复提示。

**备选方案**：直接保存原始绝对路径实现较短，但文件移动、权限变化或跨平台路径差异容易破坏重启恢复；把 base64 图片放入设置会增加读写、事件和内存成本。

### D4. 共享状态与 mock

同步扩展 Rust `Settings`/patch 或专用背景命令、序列化 DTO、TypeScript `Settings`/`Backend`、Tauri adapter、Zustand 与 MockBackend。旧设置缺少背景选择字段时，优先保留已有自定义图片；无自定义图片时使用内置默认图。无背景一经选择即显式持久化；旧版从未记录是否主动移除过背景，因此无法区分该历史意图。保留现有原子保存、revision、`settings://changed` 及跨窗口更新语义。主题切换不得清空输入、设置草稿或活动翻译。

浏览器 mock 用隔离的模拟资源实现选择、预览、替换、移除和失败场景；预览数据仅保存在内存，不依赖对象 URL。真实磁盘操作和跨窗口事件仍需 Tauri 集成验证。

### D5. 平台合成与性能

先实现受控最小验证：在 macOS/Windows 上分别检查窗口透明、图片位于 WebView 层内的模糊、窗口外部内容、非激活浮窗、DPI 与可访问性设置。依据实测选择平台实现；当背景模糊或系统透明不可用时，采用有足够对比度的主题表面。

禁止以“图片看起来半透明”推断窗口外部桌面已经被模糊。背景采用静态图片并复用同一渲染层；不新增空闲轮询、视频或常驻动画。构建大小、首屏和空闲资源与 `docs/performance.md` 现有基线比较，并对大图和窗口缩放进行实测。

### D6. 已有 OpenSpec change 的协调

`add-yiyu-desktop-translator` 尚未归档，`openspec/specs/` 当前为空；其 `translation-workspace` delta 和 `design.md` D13 仍固定 8px 圆角、无页面级渐变和打开主窗口即显示左侧历史。本次用户认可的新方向允许更大的玻璃圆角、可选图片及窄窗历史折叠。

实施前应先协调该在途 change 的相应视觉和布局文本，使其与本变更一致，同时保留其现有非视觉行为及已完成/未完成任务的事实；不得把尚不存在的主规格伪装成已归档规格。协调方式及完成记录应随两个 change 一起核对，避免未来归档时互相覆盖。

## Risks / Trade-offs

- 图片亮度和细节变化使文字对比不足 → 根据主题使用稳定遮罩，并覆盖亮图、暗图及高对比图验收。
- 系统合成能力或窗口外内容模糊不一致 → 先做平台 spike；不可用时使用可读的主题回退，不夸大平台效果。
- 大图片解码、模糊层叠或多窗口复制造成卡顿 → 限制资源、复用背景层并记录首屏/空闲基线。
- 设置保存与图片文件操作发生部分失败 → 使用候选资源、revision 校验、原子提交及有界清理，旧资源在提交前保持可用。
- 两个进行中的 change 对视觉契约冲突 → 在实施和归档前明确协调 D13、`translation-workspace` 与本变更，不重写原任务完成历史。
- 原生系统控件可能保留平台颜色及形态 → 按平台惯例和实机效果处理，不以网页模拟代替真实窗口控件。

## Migration Plan

旧配置有已保存图片时继续使用该图片；没有图片时展示默认自然风景，用户可以在外观中选择无背景。首次启动使用已有主题与玻璃设置。完成外观组件和背景导入后，依次迁移四类窗口并保留旧 IPC 行为；迁移失败时可禁用背景并回退主题表面。发布前执行视觉、交互、设置迁移和双平台真实窗口验收；未完成的旧 change 真机项保持未完成。

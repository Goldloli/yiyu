# Design

## Context

现有架构是 Tauri 多窗口、React/Zustand、Rust 桌面层和 `yiyu-core`。`src-tauri/src/commands.rs` 同时处理 IPC、翻译编排、设置、密钥、历史和更新；`state.rs` 既持有资源也负责请求并发与历史重试；`web/src/lib/store.ts` 管理所有窗口状态；设置与浮窗包含独立的视觉和业务判断。近期已修复部分并发及更新问题，但这些修复不等于架构重构完成。

现有两项未归档变更定义了翻译、取词、窗口、外观和数据行为。它们仍是行为边界；本方案不重写其已完成记录，也不把已经通过的模拟测试误称为原生系统验收。

## Goals / Non-Goals

**Goals:**

- 让每个翻译流程有明确的状态所有者；窗口只负责展示，桌面命令只处理输入输出，业务和系统细节分开。
- 在原有窗口、背景、深浅主题、权限和快捷键上建立一致、克制的视觉体系。
- 分阶段交付，保持每一步均可独立构建、测试、回退，并保护用户数据。

**Non-Goals:**

- 不更换 Tauri、React、Zustand 或 SQLite；不为了分层增加服务进程、插件体系和不必要的 crate。
- 不改变翻译协议、已有密钥命名空间、历史数据、用户配置或默认快捷键。
- 不宣称浏览器截图可以证明 macOS/Windows 原生透明、取词、权限和多屏行为。

## Decisions

### 1. 目标边界

```text
React 窗口 / 组件
  ↕ 现有命令和事件（名称、字段、错误语义保持兼容）
Tauri 命令：参数转换和系统生命周期
  ↕
应用流程：翻译会话协调、设置/凭据操作、更新流程
  ↕
yiyu-core：语言、模型请求、流解析、设置和历史
  ↕
macOS / Windows 适配：选区、剪贴板、凭据、窗口、快捷键
```

先将可独立测试的会话协调从 `AppState` 中提取，再按翻译、设置/服务商、历史、系统、更新拆分命令文件。`AppState` 只组装共享依赖；命令保留现有名称，事件和错误由边界统一映射。业务状态只保留一处权威来源，避免前端和 Rust 重复维护互相冲突的状态。

只在真实平台或可替换的网络/存储边界引入接口；先使用现有具体类型，不把每个函数包装成 trait。相比一次重写或建立层层抽象，这样能逐步缩小耦合并持续运行现有测试。

### 2. 翻译与系统能力

取词、剪贴板翻译和手动翻译进入同一个会话协调规则：同一界面的新意图淘汰旧意图；旧事件、失败和取消不能影响新会话；跨界面互不取消。模拟复制与剪贴板读写保持串行，完成恢复或确认用户剪贴板已变化后才释放。流式结果、局部结果、取消、错误及历史保存结果分别可见。

macOS 回退按项目读取剪贴板，使用临时独立剪贴板预检全部格式，并通过原生接口分别恢复多项目和旧式文本、HTML 类型；预检后再次确认用户剪贴板未变。承诺文件和其他无法可靠恢复的格式仍被拒绝，这些场景需要原生取词或手动复制。多项目的系统级验收继续跟踪 `translate_app-80k.13.20`。

macOS 和 Windows 的选区、系统授权、全局快捷键、窗口定位只留在平台适配层。日志只记录状态和脱敏元数据，不记录原文、译文和密钥。

### 3. 配置、历史和凭据

设置定义和持久化分开：设置模型负责字段与校验，存储层负责 revision、原子写入和旧数据保护。相同配置版本的未知字段留在存储层，按服务商标识与可识别字段一起保存，不传给界面，也不会恢复用户主动删除的服务商或请求头。遇到更高的配置版本时停止读取并显示升级提示，不以默认设置覆盖原文件。已有历史 SQLite 和背景资源继续原地使用。新增迁移必须向后读取旧格式、在副本上测试并可回退；不为本次结构整理做破坏性数据库迁移。

删除服务商时，设置和钥匙串是两个独立系统，不能假装具备跨系统事务。设置文件以兼容旧版本的可选字段记录待清理的服务商标识，并与服务商删除一起原子写入；成功清理后移除标识。失败时在设置中提供重试，重新添加相同标识时不删除其密钥。配置和日志中均不写入密钥；已经发布的旧版本不具备未知字段保护，回退到那些版本后重新保存仍可能丢弃新增字段。

### 4. 更新和网络

将版本检查、下载/断点、校验和安装的状态转换与平台安装操作分离，继续使用现有下载与校验流程；失败、取消、损坏文件和重新启动必须可恢复。网络代理、超时、SSE 解析和服务商错误的约束在具体边界测试，不以重构为由改动默认行为。

### 5. 前端视觉和状态

共享一套字号、间距、圆角、边框和主题语义；内容优先，选中态用轻微的表面色差。玻璃只使用柔和半透明与背景模糊，不加光带、强辉光、立体边缘或装饰性动画；背景关闭或系统不支持时回退到可读底色。

浮窗作为第一条完整纵切：安静的语言方向与必要窗口操作、可收起的原文、优先阅读的译文、紧凑操作区；空态、准备、流式、失败、取消、长文本都保留对应操作。窗口打开无装饰性动效，键盘焦点和错误提示保持清楚。完成后依次检查主窗口、设置各页、首次配置、弹窗和菜单栏，合并重复状态或说明；不删必要的权限、错误、隐私和不可逆操作信息。

`store.ts` 先明确共享设置、每窗口会话和界面局部状态边界，再按需要拆分；不新增状态框架。测试以用户动作和 IPC 契约为单位，避免只验证组件内部实现。

### 6. 分阶段验收

1. **基线**：确认现有自动测试、截图和本机授权/划词链路；记录平台缺口。
2. **浮窗与会话**：完成浮窗纵切；把会话协调器从资源容器中提取，保持现有并发与取消行为。
3. **命令与数据**：按职责拆命令，覆盖配置 revision、历史、凭据删除失败和背景更新；新增配置字段必须兼容旧配置，不能改变现有数据含义。
4. **其余前端**：逐一审阅主界面、设置、首次配置及所有应用内弹层，收敛视觉组件与冗余文案。
5. **系统与发布**：验证更新、权限、系统菜单、自动启动、快捷键、多屏和安装；分别记录 macOS 与 Windows 实机结果。

每一阶段以相关单元/集成测试、前端类型检查和交互测试为门槛；涉及视觉时检查浅深主题、有无背景、窄窗、长文和错误状态；涉及平台时追加真实系统验收。所有未验收项留在 Beads 中。

## Risks / Trade-offs

- [IPC 或事件重命名造成旧窗口失效] → 先保留接口和 DTO，逐项补契约测试，再移动实现。
- [取词与窗口时序回归] → 保留并发测试，使用独立临时数据与真实文本编辑器重测，不操作用户剪贴板中的真实内容。
- [无签名证书时授权身份变化] → 本机开发继续使用已有稳定本地签名；正式发布换签仍可能需要重新授权，不能在代码中绕过系统权限。
- [玻璃降低亮暗背景下可读性] → 采用主题遮罩和无模糊回退，分别检查亮图、暗图及系统窗口合成。
- [凭据操作部分失败] → 显示准确结果并保留可恢复路径；在隔离环境测试，不碰用户真实密钥。
- [仅有 CI 无法覆盖 Windows 桌面行为] → 明确记录缺口，不将 Windows 构建成功等同于实机验收。

## Migration Plan

1. 先增加测试并按模块提取；每个提交保持当前配置、历史数据库、背景文件及密钥可被旧版本读取。
2. 若将来确需数据迁移，先备份并支持旧版本读取；不得在用户数据上试验迁移失败分支。
3. 回退结构或视觉变更时回退对应提交；除非另有经验证的迁移策略，不删除配置、数据库、系统凭据或授权记录。
